# 09 - 代码质量改进计划

> 起草日期: 2026-05-16
> 范围: 当前 28 个未提交修改文件 + 相关全仓清扫
> 目标: 清理近期"抽象只搭骨架未落地"造成的过渡态债务,使新引入的 BaseRepository / AIConfigRepository / access_helper 等抽象真正取代旧调用

---

## 0. 背景

近期一轮重构方向正确(抽 `BaseRepository[T]`、抽 `AIConfigRepository`、抽 `access_helper`、把 handler 中 `h.db.` 直查迁到 repository),但每一处抽象都"只搭骨架未把肉搬过去"——新封装与老调用点并存,短期内 DRY 反而比重构前更严重。本计划把这些"半步"补齐。

审查发现详见会话内审查报告(死代码/DRY/KISS/SOLID 四维),本文档只承载**可执行的改进任务**。

## 1. 阶段划分

| 阶段 | 性质 | 风险 | 工作量(粗估) |
|------|------|------|--------------|
| P0   | 删死代码、机械替换 | 极低 | < 0.5d |

## 2. P0 - 即清死代码(无行为变化)

### P0.1 删除 handler 包内死函数 `createActivityLog`

- **文件**: `internal/handler/helper.go:54-69`
- **原因**: `service/activity_log.go:8` 已有同名函数,被 `story_service.go`/`task_service.go` 调用 20+ 次。handler 包这份从未被引用,仅造成命名冲突隐患。
- **动作**: 删除整个函数定义。
- **验收**: `grep -r "handler.createActivityLog\|h\.createActivityLog" internal/` 为空;`go build ./...` 通过。

### P0.2 删除手写 `min` 函数

- **文件**: `internal/service/ai_service.go:795`
- **原因**: Go 1.21+ 已内建 `min` / `max`。`go.mod` 已是 1.21+。
- **动作**: 删除自定义 `func min(a, b int) int`;若调用点签名不匹配自动适配。
- **验收**: `go vet ./...` 通过;`go test ./internal/service/...` 通过。

### P0.3 删除各 repo 的冗余 `db` 字段与 `FindByID` 覆盖

- **影响文件**:
  - `internal/repository/story_repo.go:8-25` (`db` 字段 + `FindByID`)
  - `internal/repository/sprint_repo.go:8-26`
  - `internal/repository/project_repo.go`
  - `internal/repository/bug_repo.go`
  - `internal/repository/task_repo.go`
  - `internal/repository/user_repo.go`
  - `internal/repository/activity_repo.go`
  - `internal/repository/bug_comment_repo.go`
  - `internal/repository/testcase_repo.go`
  - `internal/repository/ai_config_repo.go`
  - `internal/repository/board_column_repo.go`
- **原因**: 每个 repo 内嵌 `BaseRepository[T]`(已含 `db`),又重复声明独立 `db *gorm.DB`,且部分 repo 覆盖了与基类完全一致的 `FindByID`,纯粹遮蔽。
- **动作**:
  1. 删除子 repo 的独立 `db` 字段。
  2. 构造函数中只保留 `BaseRepository: NewBaseRepository[T](db)`。
  3. 子类内部所有 `r.db.Xxx` 改为 `r.DB().Xxx`(`BaseRepository.DB()` 已暴露)。
  4. 删除与基类签名/行为一致的 `FindByID` 覆盖。若子类需要 Preload 关联(如 `FindByIDWithDetails`),保留并改名清晰。
- **验收**: 所有 repo 不再持有 `db *gorm.DB` 字段;`go test ./internal/repository/...` 全绿;`go test ./...` 全绿。

### P0.4 替换 search_handler 中的手写冒泡排序

- **文件**: `internal/handler/search_handler.go:581-587`, `791-797`, `805-811`
- **原因**: O(n²) 手写排序,可读性与性能都差。
- **动作**: 三处全部改为 `sort.Slice(arr, func(i, j int) bool { return arr[i].Score > arr[j].Score })`。
- **验收**: `grep -n "for j := i + 1" internal/handler/search_handler.go` 为空;搜索接口结果次序不变(已有单测覆盖应保持绿色)。

### P0.5 修复 `techlead_handler.ListWorkload` 用户信息丢弃

- **文件**: `internal/handler/techlead_handler.go:215-219`
- **现状**:
  ```go
  for _, devID := range developerIDs {
      var user model.User
      if _, err := h.userRepo.FindByID(devID); err != nil { continue }
      ...
      workloads = append(workloads, gin.H{
          "user": gin.H{"id": user.ID, "email": user.Email},  // 永远 0/""
          ...
      })
  }
  ```
- **动作**: 改为 `user, err := h.userRepo.FindByID(devID); if err != nil { continue }`,后续使用 `user.ID` / `user.Email`。
- **验收**: 接口 `GET /api/techlead/workload` 返回项 `user.id`/`user.email` 非零;补一个 handler 级测试用例。

### P0.6 删除 self-praise 注释

- **文件**: `internal/handler/search_handler.go` 中 `// DRY:提取公共方法`、`// KISS:保持简单` 等
- **原因**: 这类注释不传递信息,只是"提醒原则存在"。
- **动作**: 批量删除;真正非平凡的"为什么"才保留注释。
- **验收**: 文件检索无 `KISS|DRY|SOLID` 字样的标语类注释。

### P0.7 修正 `bug_comment_handler.truncateForLog` 注释

          api.Forbidden(c, "非项目成员无法访问")

## 4. P2 - 中等重构

### P2.1 抽取鉴权中间件,消灭 80 处样板

- **现状**: `userID, ok := middleware.CurrentUserID(c); if !ok { Unauthorized; return }` + 角色判断 + `parseUintParam("id")` + `ensureProjectAccess` —— 在 80+ 个 handler 方法中复制粘贴。
- **目标**: 用 Gin middleware/装饰器接管前置校验,handler 函数内只处理业务。
- **拟新增中间件** (放在 `internal/middleware/access.go`):
  1. `RequireProjectAccess(paramKey string)` — 取 URL 参数 `paramKey` 作为 projectID,执行 `service.EnsureProjectAccess`,把 `*model.Project` 与 `isOwner` 注入 `c.Keys`。
  2. `RequireStoryAccess(paramKey string)` — 同理。
  3. `RequireRoles(...)` 已存在(`router.go:228`),需要在路由层成体系铺开使用。
- **路由改造示例**:
  ```go
  protected.PATCH("/stories/:id/status",
      middleware.RequireStoryAccess("id"),
      storyHandler.UpdateStatus)
  ```
- **handler 内取数**:
  ```go
  story := middleware.MustStory(c)  // 来自中间件注入,绝不为 nil
  ```
- **验收**:
  - handler 中 `middleware.CurrentUserID` 出现次数从 80+ 降到 10 以下(仅保留写入/审计场景需要 userID 的位置)。
  - `errForbidden`/三段式 access error 分支基本消失。
  - 全部 handler/integration 测试保持绿;新增 1-2 个中间件单测。

## 5. P3 - 架构层调整(可选,改动面大)

### P3.1 Handler 依赖 repo/service 接口而非具体类型

- **目标**: 测试时可以 mock,不必每次都拉真 DB。
- **示例**: `ProjectHandler` 当前持有 8 个具体 repo,改造为持有 8 个接口(`StoryReader`、`MemberWriter` 等),具体 repo 实现接口,构造时注入。
- **优先级**: 中。若仍以集成测试为主,可推迟;若计划补 handler 单测,则需要先做。

### P3.2 拆分 `service.AIService` 大接口

- **现状**: 单接口囊括 generate / split / INVEST / refine-AC / summary / translate / DoR。
- **拟拆分**:
  - `StoryGenerator` (生成/拆分)
  - `StoryAnalyzer` (INVEST/DoR)
  - `StoryTransformer` (refine-AC/summary/translate)
- **影响**: `openAIService` 与 `heuristicAIService` 各自实现所需的小接口,handler 仅依赖需要的子集。
- **代价**: 调用点 import 需调整;若 AI 接口仍在快速演化,可暂缓。

### P3.3 引入轻量 DI 容器或显式 wiring 层

- **现状**: `router.go:71-92` 直接 `NewXxxHandler(db)` 顺序构造,handler 间通过 `WithEvents`/`WithNotifier` 二次注入,混乱。
- **拟动作**: 引入 `internal/wiring/wiring.go`,集中持有所有 handler/service 实例并完成接线;`router.New` 只负责注册路由。
- **优先级**: 低。当前规模 router.go 还可读;handler 数破 30 之前不必上。

## 6. 不在范围内 / 显式不做的事

- **不引入新的 ORM 抽象层**: BaseRepository 已足够,不再叠加 `Specification` / `QueryObject` 模式。
- **不重写测试框架**: 现有 testify + httptest 路线保持。

- **不一次性提交**: 每个 P0/P1 子项作为独立 commit,便于回滚与 review。
